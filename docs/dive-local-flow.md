# 本地深潜流程与原服数据边界

本说明依据当前游戏表、原 Android `Assembly-CSharp.dll`，以及恢复的上游 `feature/dive` [提交 `cfa17a69`](https://github.com/MadlyMoe/RevivalSide/commit/cfa17a693064926acda7bbe265c676f922102b27)。用户选择恢复该开源分支已有的混合节点流程。上游源码中的权重属于该项目实现；原官方服务器分组概率仍未获得。

## 坐标、战斗与终点

| 字段 | 含义与约束 |
| --- | --- |
| `floor.stageID` / `diveStageID` | 探索坐标，例如 1020；不是单场战斗的 dungeonID。 |
| `DEPTH` | 大区深度。1010 至 1050 同属深度 1，1060 开始深度 2。进入下一坐标不一定进入下一深度。 |
| `RANDOM_SET_COUNT` | 当前坐标节点行数；每行选择一个战斗、修复或遗物节点，然后进入独立的最后一行 Boss。1020 为 2 个可选节点加 1 个终点。 |
| `sectorType` | 地图图标和扇区分类，普通类型为 4/6/8，困难类型为 5/7/9；终点 Boss 类型为 2/3。 |
| `eventType` | 节点行为。普通战斗为 1，探索终点 Boss 为 2；普通战斗模板自身也可能是 `NDT_BOSS_KILL`，这种击杀任务不会结束探索。 |
| `eventValue` / `dungeonID` | 单场战斗模板 ID。使用上游生成器从真实表导出的活跃现代 Dungeon 池，不使用旧 8 级模板作为新流程候选。 |
| `distance` | 已完成的节点数。预留战斗时不增加，胜利时增加一次。 |
| `slotSetIndex` / `slotIndex` | 第一次待战行索引为 0，后续待战为 1，完成后行索引压回 0，但保留选中的路线位置。原生 UI 把完成行 `Slots[0]` 放到该位置，下一行可选范围为该位置 ±1。 |
| `diveUid` + `diveDistance` + 节点/编队 | 单场结果归属。滑动窗口反复使用索引 1，必须同时检查绝对距离，避免旧结果结算到新节点。 |

状态转换如下：

| 阶段 | 状态 | 距离与地图动作 |
| --- | --- | --- |
| 开始坐标 | Exploring=0 | `distance=0`、`slotSetIndex=-1`，首个可选行是 0；不插入 START 占位行。 |
| 选择普通节点或终点 | BattleReady=1 | 保留已完成距离，设置当前节点和待战 dungeonID。 |
| 加载战斗 | BattleLoad=2 | 预留指定存活编队；加载失败精确回滚至 BattleReady。 |
| 普通节点胜利 | Exploring=0 或 SelectArtifact=4 | 按原生 `Floor.Rebuild` 保留本次选中的单槽、移除上一行；增加距离，行索引回到 0，保留路线位置。精英战胜利提供遗物候选。 |
| 修复/补给/地图遗物 | Exploring=0 或 SelectArtifact=4 | MOVE_ACK 先以旧下一行和新路线位置重建，再复制玩家与编队数据；该节点立即占一行，不发送 GAME_LOAD。 |
| 选择遗物 | Exploring=0 | 1215/1216 只更新玩家和遗物，不再重建楼层、不增加距离。 |
| 战败 | Exploring=0 或 Annihilation=5 | 本次编队舰船 HP 清零；存活编队退回上一已完成位置，可重选失败列或合法相邻节点，距离和楼层不变。保留失败编队 ID 供船毁动画使用，死亡编队排除助战。全部编队死亡时停止。 |
| 最后一行 Boss 胜利 | Clear=6 | 同时满足 Boss 事件、`distance=RANDOM_SET_COUNT`、当前行是最后一行，才发探索奖励并移除 active Dive。 |
| 下一坐标 | 新的 START_REQ | 由客户端另发 1206，创建新的探索 UID 和满血编队；当前坐标普通节点不会主动创建下一坐标。 |

旧版本记录中，1030 和 1040 都完成了两个普通节点及第三场旧模板 `9410013` 后，再开始下一坐标。恢复后的 1020 末战使用现代池的 `9500012`（`NKM_DIVE_BATTLE_SL04`）；这是上游按坐标选择的分组 Boss。战斗包另带 `diveIsBoss`，普通战斗自身的 `NDT_BOSS_KILL` 不会被误判为探索终点。

## 敌人等级与编队作用

探索 1020 的表为 `STAGE_LEVEL=32`、`STAGE_LEVEL_SCALE=2`、`SET_LEVEL_SCALE=5`。新流程使用基准 30 的现代战斗池；旧版本曾选择基准 8 的旧模板，造成标称等级与实际敌人不符。

所有坐标沿用上游运行时目标 `diveLevel = STAGE_LEVEL + 终点Boss的SET_LEVEL_SCALE`，再用真实 `dungeon.m_DungeonLevel` 计算增量。战斗层显式传递 `m_TeamBLevelFix=0`，保留怪物间原有等级差异：1020 普通基准 30 加 2 得到 32，末 Boss 加 7 得到 37。普通节点不按距离额外叠加 5。51 坐标普通/末 Boss 为 131/136（基准 130，加 1/6），80 坐标为 160/170（基准 155，加 5/15）。世界地图变体使用自己的 `SET_LEVEL_SCALE`，例如 10180 的 Boss 为 160。

现代池的基础等级与原生预览公式一致。生成器早期将 51–80 的基础等级误记为目标等级；现已修正派生信息，使其与上游运行时和当前实战一致。模板的 `DIVE_MONSTER_BC` 也传为真实战斗条件，例如 `BC_DIVE_DEPTH_7` 对应 41031，表内使用敌方 Buff 列表，不施给主战编队。

主战编队舰船 HP 按实战快照保存为比例，下一场使用同一比例。其他存活编队仅提供各自已配置的队长作为助战，保留其等级、技能、突破和装备；空编队、死亡编队、主战队及重复 UID 排除。助战进入原生 `m_listAssistUnitData`，不把整个其他编队混入主战卡组。

本地保留无限战斗次数：弹药不扣减、不作为服务端参战门禁。显示弹药与原生规则对齐，默认 2、补给上限 2；死亡编队仍不可参战。

## 当前随机节点覆盖

对原始资源包的 22378 份 Lua 字节码进行搜索，`SLOT_EVENT_GROUP_ID`、`BOSS_EVENT_GROUP_ID` 仅在 `LUA_DIVE_TEMPLET` 的两份镜像出现，没有独立事件权重定义。本次恢复上游已有规则：每行 slot 0 保留战斗路线，其余位置战斗/修复/遗物权重为 32/8/9；每次探索最多生成一个地图修复和一个地图遗物，战斗节点精英概率为 35%。seed 使用探索 UID，重登不重抽，新探索可变化。

现代池由 `tools/generate-dive-dungeon-pools.js` 从当前真实表生成，默认输出运行时使用的 `gameplay-jsons/generated/dive-dungeon-pool.json`：80 个坐标编号、12 组基础等级、134 个 Dungeon，覆盖全部 160 个全局与世界地图模板。Boss 分段选择保留上游实现。旧版本正在进行的探索不强制重建；放弃后重新 START 才使用新的混合路线。

| 原生节点 | 客户端证据 | 当前本地状态 |
| --- | --- | --- |
| 普通战斗 1、终点 Boss 2 | 原生事件枚举、战斗模板、移动/结算协议 | 支持，按上述终点条件推进。 |
| 空白 5 | 原生事件枚举 | 保留节点，立即占一行；上游生成器不生成。 |
| 修复 6、遗失舰船修复 11 | 原生枚举，`DiveRepairHP_RATE=20` | 修复节点恢复存活舰船 20% 最大 HP，上限为满血，不复活死亡编队。生成器只生成 6。 |
| 补给 7、遗失舰船补给 12 | 原生枚举，`ChangeSupply` 上限为 2 | 已有节点按 +1、上限 2 执行。上游生成器不生成补给，没有另加概率。 |
| 物品/单位 3/4、9/10、16/17 | 原生枚举 | 保留上游奖励动作；生成器不生成，不能称原服分组奖励。 |
| 遗失舰船/信标随机 8/13、信标 14/15/18 | 原生枚举 | 保留上游分支动作与权重；生成器不生成，未新增这些节点的抽样概率。 |
| 遗物 19 | `LUA_DIVE_ARTIFACT`、选择协议 1215、状态 SelectArtifact=4 | 提供 3 个未持有候选，选择后继续；精英战也提供遗物。持有上限 8，超限返还奖励按原遗物表。效果映射到真实 `m_RefBattleCondition_ID`。 |

## 验证方式

`tools/check-dive-continuation.js` 遍历全部 160 个探索模板、960 个节点的贯通战斗路线，另检查实际混合节点 ACK、修复 20%、补给上限 2、遗物选择、三路选择、新探索变化与重登稳定。`--native-fixtures <临时JSON路径>` 输出人工测试账号的流程状态，不包含导入的私有存档。

`tools/DiveClientProtocolCheck` 使用原 Android DLL，验证 `CanMoveForward`、胜利后的 `UpdateData(true, sync)`、战败的 `UpdateData(false, sync)`、实际 MOVE_ACK 分支的先重建后复制，以及遗物选择的无重建复制。完成行单槽按原生 UI 逻辑映射到原路线位置，不错误要求 `Floor.GetSlot(0, oldLane)` 可访问。当前 3489 项原生检查通过，包含首次失败、后续偏移路线失败、全灭和重复结果；地图动画和助战按钮仍需设备测试。
